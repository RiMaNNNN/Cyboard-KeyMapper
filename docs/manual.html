KeyMapper

A local configuration app for the Cyboard Imprint wireless keyboard — live keymap editing, multi-step sequences, per-layer underglow colors, battery monitoring, and a guided custom-firmware pipeline, all built on the open ZMK Studio protocol.

1. Getting started

KeyMapper runs on Windows, macOS, and Linux: the UI is a browser page and the server is plain Python. On Windows, launch it by double-clicking KeyMapper.bat (or its desktop shortcut); on macOS and Linux run ./keymapper.sh. Either starts the local server, opens your browser at http://127.0.0.1:8756, and shuts everything down by itself a few seconds after you close the tab. Windows uses the native Bluetooth stack and is tested daily on real hardware; macOS/Linux use the cross-platform Bleak backend (not yet validated on a physical keyboard — see the README for setup details and the Linux serial-permission note). Features that type at the computer — Alt-code accents, the Win+R program launcher — target whatever machine the keyboard is plugged into, and those two assume a Windows host.

  1. Plug the left half of the keyboard into the PC with a USB-C data cable (many USB-C cables are power-only — if nothing happens, try another cable). KeyMapper finds and connects to the keyboard automatically; there is no port picking.
  2. On stock (factory) firmware the keyboard boots locked: hold the two left-half home-row keys at the positions where A and F sit in the factory layout for about three seconds. This reads physical positions, so it works no matter how the keys are remapped. After you flash KeyMapper-built firmware once, locking is gone permanently (unless you re-enable it in the Advanced tab).
  3. Click Back up now in the Backups tab. Until you do, your layout exists only inside the keyboard.
Only the left half talks to the app — it is the split keyboard's "central". The right half needs a USB cable only when flashing firmware onto it.

2. Concepts: layers, behaviors, bindings

A layer is a complete set of key meanings. Layers stack: the highest active layer wins for each key, and Transparent keys fall through to the layer below. Layer 0 is always active.

A behavior is what a key does: send a keycode, switch a layer, control the underglow, run a sequence. A binding is one key position on one layer pointing at a behavior with up to two parameters.

Edits you make are applied to the keyboard instantly but live in RAM ("pending"). Save writes them to the keyboard's flash so they survive power-off; Discard reverts pending edits. KeyMapper always writes a file backup before saving.

3. Home tab

The Home tab is a status dashboard: the connection card on top and the battery card below it. Everything configurable lives elsewhere — editing in the Editor and Sequences tabs, firmware-level tweaks in the Advanced tab.

Connection

Shows whether the left half is connected over USB (with the port name) and offers Scan now when it is not. If the connected keyboard is locked (stock firmware), the card says so and points at the Advanced tab for the guided unlock.

Battery

Battery gauges for both halves, read over the Bluetooth pairing (independent of the USB cable). Green above 40%, orange above 20%, red below. The right half's gauge requires KeyMapper-built firmware (it adds a "battery proxy" so the left half re-publishes the right half's level). A low or sagging battery dims and color-shifts the underglow — mixed colors like yellow show it first — and can cause flicker. For a check without the app, assign the BattCheck behavior to a key (see the Advanced tab chapter): each half flashes its own level as a red-to-green color.

4. Editor tab

The board is drawn from the keyboard's own geometry — every key at its true position, including rotated thumb clusters. Key labels are color-coded: letters in the default ink, numbers blue, F-keys purple, keypad cyan, layer keys orange, mouse pink, sequences green, and disabled keys dimmed.

Editing a key

Click a key to open the binding editor: pick a behavior (the list is alphabetical and comes from the keyboard itself), then set its parameters. For key presses the keycode catalog is searchable and grouped into categories — Letters, Numbers, Nav & symbols, F-keys, Keypad, Modifiers, Media, App Launch, and App Control — add modifiers with the LS/LC/LA/LG chips, or click “Press a key…” and just press it — on this computer's keyboard for a plain keycode, or on the keyboard itself to copy that key's full binding (see below).

App Launch and App Control keys

App Launch (AL) keys are standardized HID codes that ask the operating system to open a program: calculator, internet browser, email, file manager, lock screen, task switcher… What opens is decided by Windows; the keyboard only sends the standardized request.

App Control (AC) keys act inside a program: Copy, Paste, Undo, Find, browser Back/Forward/Refresh/Home, Zoom, Scroll… They are delivered to the keyboard-focused (active) window — the mouse position is irrelevant — and they are requests: the app handles the commands it understands (Copy/Paste/Undo and browser navigation are near-universal) and silently ignores the rest; a few are handled by Windows itself. Nothing errors when an app does not support a command — the key simply does nothing there.

Opening any program, file, or URL from a key

A keycode cannot carry a file path, so KeyMapper offers launcher sequences instead: Sequences → “Open program / file…” builds a sequence that taps Win+R, types your path, command, or URL, and presses Enter — Windows then opens it exactly as if you had double-clicked it. Works for executables, documents, folders, and web links. The typing assumes a US-QWERTY Windows keyboard layout.

Super Fast Assign

Tick Super Fast Assign, hover any key on the board, and press a key on your computer's keyboard — assigned instantly, no dialog. Clicking a key still opens the full editor for things a plain keyboard can't express.

Assign by pressing a key on the keyboard itself

Super Fast Assign and the binding dialog's Press a key… button also listen to the keyboard itself. Press any of its keys and the app copies that key's complete binding — a sequence, a layer switch, an underglow command, anything — from the layer selected in the editor onto the target key. This works because KeyMapper-built firmware publishes the last pressed key position over the Bluetooth bond (a tiny read-only characteristic, like the battery level); a normal keyboard press can only convey a plain keycode, which is why other keyboards cannot do this.

  • Requires KeyMapper-built firmware — flash the latest build once (Firmware tab) — and the keyboard paired to this PC over Bluetooth (the position report travels over the Bluetooth bond, like the battery levels). On older firmware, or without the pairing, the capture modes silently fall back to computer-keyboard-only.
  • The pressed key still performs its action while you capture: a "To Layer" key really switches the keyboard's layer (and its underglow color), and a sequence really types its output. Harmless, but expected.
  • When a pressed key also types visible output (letters, sequences), the app waits half a second and prefers the full binding reported by the keyboard over the raw typed keycode.
  • On current KeyMapper firmware every press is pushed to the app within tens of milliseconds, so each press pairs with the key you were hovering when you pressed — you can work fast. Older capture firmware falls back to polling, where it is best to keep hovering the target until the assignment appears.
  • The press captures what the key does on the keyboard's active layer at that moment (Transparent falls through, exactly like ZMK resolves a real press). So if a sequence just switched the keyboard to layer 1, pressing the same physical key now captures its layer-1 binding — e.g. to_layer_2 — regardless of which layer the editor is displaying. On older capture firmware without layer reporting, the editor-selected layer is used instead.

Multiple selection

Tick Multiple selection and taps toggle keys in and out of a selection. Then: Copy, Cut, Paste (click an anchor key — the copied cluster lands on the geometrically matching keys; the anchor is the top-left key of what you copied), Assign Selection to… (any behavior), or assign the whole selection to NONE / TRANSPARENT. Every operation is one undoable step.

Trackball icons

Round ball buttons sit in the gap between the halves — one per installed trackball. Clicking one opens that ball's settings (mode, speed, direction, responsiveness — see the Advanced tab chapter). The balls are not keys: Super Fast Assign and multi-select ignore them.

Layers panel

Select, add, rename, reorder, or disable layers. Assign color in a layer's menu opens the color map and recolors every sequence that switches to that layer. Undo / Redo cover all binding edits of the session.

5. Sequences tab

A sequence (ZMK "macro") runs several behaviors from one key press. ZMK compiles sequences into the firmware — that is a property of the keyboard firmware itself, not an app limitation — so the workflow is: compose here, build & flash once in the Firmware tab, then assign the sequence to any key in the Editor like a normal behavior.

Presets

  • Accented letters — è/É-style Shift pairs: plain press types the lowercase Alt-code, holding Shift types the uppercase one. The held Shift is masked while the sequence types (otherwise it would corrupt the keypad digits). Sequences switch Num Lock on automatically when needed and restore it afterwards (the host reports its lock LEDs to the keyboard).
  • € (Alt+0128).
  • To <layer> + color and Hold <layer> + color — generated live from your current layers and their colors, so they always reflect what you set in the Editor or Advanced tab. The Hold variant wraps itself in &rgb_mem: on release the underglow returns to exactly the color it had before the hold.

Composer rules

  • Steps are behaviors in devicetree form (&kp LS(A), &to 1, &rgb_ug RGB_COLOR_HSB(120,100,50)). Comma-separated behaviors in one step are split automatically.
  • Colors are HSB: hue 0–360 (0 red, 60 yellow, 120 green, 240 blue), saturation and brightness 0–100 — not RGB bytes.
  • A sequence used by any key must keep its display name unchanged across firmware rebuilds; the name is what re-links keys to it.
  • A SHIFT variant, when present, runs instead of the plain steps while Shift is held.

6. Advanced tab

The settings on this tab are compiled into the firmware: change one, then rebuild and flash BOTH halves in the Firmware tab for it to take effect. Both halves share the same settings. One exception: trackball mode, speed, and direction also apply live over Bluetooth on firmware that carries KeyMapper's config channel — see below.

Studio locking

Stock firmware boots "locked": no configuration app (KeyMapper or Cyboard Studio) can read or change the keymap until you hold the two physical keys at the factory A and F positions for about three seconds — after every restart. KeyMapper-built firmware disables that lock by default, and keeping it disabled is the advised setting: the lock only guards configuration changes coming from the computer, never your typing. If you prefer the stock behavior, switch Keep ZMK Studio locking on — then KeyMapper requires the physical A+F unlock every time the keyboard restarts. When the connected keyboard is locked right now, this card also shows the guided unlock instructions.

Trackballs

Configures what each ball does when rolled — Cursor (moves the pointer), Vertical scroll, Horizontal scroll, or Disabled — with a per-ball speed (as a percentage; the stock left-ball scroll uses 33%) and a natural direction toggle for scroll modes (the view follows the top of the ball, the stock feel). Responsiveness is the minimum time between motion reports in milliseconds, shared by both sensors: lower is snappier but costs battery and Bluetooth airtime (stock: 8 ms). Three wake controls determine how fast a ball reacts after sitting still: Wake check is how often a resting sensor looks for motion (stock rests in tiers down to one check per 500 ms — a long-idle ball can take up to a second to react; 10 ms is near-instant but drains more); Stay awake after motion is how long the sensor holds full speed after the last movement (stock 128 ms); and Force awake makes the sensors never rest at all — the infinite stay-awake with zero wake lag, at the highest sensor battery cost. The keyboard-level idle and deep-sleep timeouts (Power & idle above) still apply with Force awake on, so the half as a whole still sleeps. Leave fields empty / the switch off for stock behavior. All timing settings are build options: rebuild and flash to apply. An Installed switch per side tells KeyMapper which balls your board physically has — the keyboard cannot report that itself. It controls which ball icons the Editor shows AND compiles that ball off in the next firmware build, so only untick it for a side that truly has no ball. The same settings open by clicking the round ball icons between the halves in the Editor tab. Speed is applied as the closest scaling fraction the firmware supports, so some values are rounded slightly (a few percent at most).

Live, no rebuild: on KeyMapper firmware that includes the trackball config channel, Apply/Save writes mode, speed, and direction straight to the keyboard over the Bluetooth pairing — they take effect instantly and persist across restarts, exactly like Cyboard Studio's trackball page (which uses a private channel in stock firmware; KeyMapper ships its own). The app tells you after each save whether it applied live or needs a rebuild. The firmware flushes a pending save before entering deep sleep, and the app re-applies your staged settings automatically whenever the keyboard reconnects — so a wake or reboot can never leave stale trackball behavior behind. The rest is build-time: Responsiveness, the three wake controls (Wake check, Stay awake, Force awake), and the Installed switches.
Defaults reproduce the factory behavior exactly: left ball scrolls vertically (natural direction, one-third speed), right ball moves the cursor. Cyboard Studio's trackball panel needs its private stock-firmware extension; KeyMapper's own config channel provides the same point-and-click live experience on KeyMapper-built firmware.
Scrolling whatever window sits under the mouse pointer is a Windows feature ("Scroll inactive windows when hovering over them", on by default) — no keyboard or KeyMapper setting is involved.

Power & idle

Controls the keyboard's built-in power management for battery operation. After the idle time without key presses a half goes idle and can switch its underglow off; with deep sleep enabled it powers off completely after the sleep timeout — that is why an unplugged half that sat unused seems dead until you press a key and give it a second or two to reconnect. Underglow off whenever unplugged keeps the LEDs off during battery operation entirely — the single biggest battery saver.

With Underglow off while idle, KeyMapper-built firmware relights both halves with the last color as soon as the keyboard wakes — a keypress on either half, or a half reconnecting after deep sleep. (Stock ZMK only relights the half whose own key was pressed; the split link carries no wake signal, so KeyMapper's firmware adds one.)

Layer colors

Shows the HSB color triple of every color-setting sequence, with a swatch. Click a chip to pick a new color on a visual hue/saturation map with a brightness slider. Brightness for ALL sequences rewrites just the brightness component everywhere at once. Brightness is stored on a 0–100 scale and the firmware remaps it onto its compiled output window (5%–50% on the Imprint): 0 is the darkest still-lit setting — the level the physical brightness-down key bottoms out at — not off.

The protocol has no "read current color" call, so live tweaks made with the keyboard's own hue/saturation/brightness keys cannot be read back by any software. Treat the app as the source of truth for colors.

Low-battery blink

When enabled, the half whose battery drops below the threshold blinks its underglow in the alert color, then restores your color, repeating at most once per interval. Threshold, blink count, HSB color, and interval are all configurable.

BattCheck (battery level as color)

The BattCheck behavior flashes each half in its own battery color when pressed: 0% is red, sweeping through orange and yellow to green at 100%. One press triggers both halves and each shows its own battery, so the two can differ. After the configured duration (default 2 s, set in the Advanced tab's battery card; compiled into the firmware, and capped just below the idle timeout so a glow never spans an idle transition) the previous color, effect, and on/off state return; pressing again during the glow refreshes it and restarts the timer. Assign BattCheck to any key in the Editor, or use it as a sequence step. KeyMapper firmware only: the behavior appears in the Editor's picker after you build and flash a KeyMapper build that includes it (stock firmware does not have it). Right after a restart a half may show red for up to a minute, until its first battery reading arrives. A fully asleep half cannot respond until it wakes.

7. Firmware tab (the wizard)

Five steps, in order — the job is done only after the last one:

  1. Sign in to GitHub. Firmware is compiled for free on GitHub Actions in a private repository under your account, created automatically from Cyboard's official template. The sign-in uses GitHub's own CLI (a console window plus browser approval); KeyMapper never sees your credentials, and the login is remembered across runs.
  2. Generate. Snapshots your current layout (with an automatic backup) and renders it — plus all staged sequences and every Advanced-tab setting (Studio locking, trackballs, Power & idle, layer colors, low-battery blink, BattCheck duration) — into firmware source. Review any warnings.
  3. Build. Pushes to your repository and waits for GitHub Actions (about two minutes), then downloads the two firmware files.
  4. Flash the RIGHT half. Plug the right half in via USB-C data cable and double-tap the reset button next to its USB port; a drive named ASSIMILATOR appears and KeyMapper detects it. Press the right-hand flash button.
  5. Flash the LEFT half — finishes by itself. Same procedure with the left half, then keep it on the cable: after the flash, KeyMapper automatically waits for the keyboard to reconnect, clears the old stored layout (which would otherwise shadow the keymap you just flashed — a fresh backup is written first), and verifies the result with a live countdown. No separate finalize step; if the automatic finish is interrupted, a retry button appears.
KeyMapper-built firmware also: disables the unlock combo (unless you re-enabled Studio locking in the Advanced tab), compiles in the &rgb_mem color save/restore behavior, enables the right-half battery gauge, adds the capture channel (assign a key by pressing it on the keyboard itself), applies your trackball and Power & idle settings, and (optionally) blinks the underglow on the half whose battery is low — all configurable in the Advanced tab.
Why right first? Only because the LEFT flash triggers the automatic finish, which needs the left half on the cable afterwards. Flashing in the wrong order is harmless — just make the left half the last one you flash (re-flashing is always safe), or use the retry button.
Both halves must be flashed over USB. The halves talk to each other by radio only — a cable between the two halves connects nothing — and the UF2 bootloader has no wireless mode. A failed or interrupted flash is harmless: the bootloader survives, just flash again.

8. Backups tab

Each backup is a complete snapshot: every layer, every binding, and the behavior catalog, in one portable JSON file. Backups are written automatically before every save, settings reset, and firmware generation.

  • Compare (click a backup): lists exactly which keys differ between the backup and the keyboard right now, layer by layer.
  • Restore: re-applies the backup's bindings and layer names to the keyboard as pending changes — review in the Editor, then Save (or Discard to abort).
  • Download: saves a copy anywhere you like.
  • Delete: tick one or more backups and delete them.

9. Behavior glossary

BehaviorWhat it does
Key Press (&kp)Sends one key. Modifiers can be embedded: LS(A) is Shift+A on a single key.
Transparent (▽)Ignores the press on this layer and lets the layer below handle it.
None (∅)Swallows the press completely.
Momentary Layer (MO)Layer active only while held — like Fn.
To Layer (TO)Switches to the layer and stays. Put a "To layer 0" key on the target layer to come back.
Toggle Layer (TOG)Turns one layer on/off without touching the others.
Sticky Layer (SL)Layer active for exactly the next key press.
Sticky Key (&sk)One-shot modifier: tap Shift-sticky, then A → one capital A.
Mod-Tap (&mt)Hold = modifier, tap = normal key.
Layer-Tap (&lt)Hold = momentary layer, tap = normal key.
Underglow (&rgb_ug)All lighting commands: on/off, hue, saturation, brightness, speed, effects, or an absolute color. Global — both halves follow.
RGB Save/Restore (&rgb_mem)KeyMapper firmware only: press memorizes the current color and on/off state, release restores them. Used by the Hold-layer color presets.
BattCheck (&batt_chk)KeyMapper firmware only: flashes each half in its own battery color (0% red → 100% green) for the configured time, then restores your lighting.
NumLock Guard (&nl_guard)KeyMapper firmware only: while held, makes sure the host's Num Lock is ON, restoring the original state on release. Wrapped automatically around every Alt-code sequence; rarely needed on a key of its own.
Bluetooth (&bt)Profile selection and clearing.
SequencesYour compiled macros, listed by their display names.

The "KeyMapper firmware only" behaviors (RGB Save/Restore, NumLock Guard, BattCheck) are directly assignable to keys from the Editor's picker like any stock behavior — they appear in the list once you have flashed a KeyMapper build that includes them.

10. Troubleshooting

SymptomCause and fix
Keyboard not foundUse the LEFT half; use a USB-C data cable; try another port. The app rescans automatically every few seconds.
"Keyboard is locked"Stock firmware boots locked — hold the two factory A/F-position keys on the left half for ~3 s. KeyMapper firmware never locks unless you re-enabled Studio locking in the Advanced tab (then the same hold is needed after every restart).
Accented capitals type garbage, or the Windows input language switches while typing themOld firmware build. Rebuild and flash: shifted sequence variants must run at zero pacing inside the Shift mask window (current builds do this automatically; they also manage Num Lock by themselves).
The two halves show slightly different colorsPress any absolute color sequence (e.g. a To-layer key) to resynchronize both halves. Relative hue/saturation/brightness steps can drift the halves apart if a radio packet is missed. If one half also flickers, check its battery gauge — voltage sag shifts LED color balance (yellow shows it first).
Layer keys point at the wrong layer after reordering layers Re-run the Firmware wizard's last step (flash the left half — the automatic finish realigns stored layer identities with positions), or use its retry button.
Flash appears to fail with a copy error at the very endNormal: the keyboard reboots before Windows gets its final acknowledgement. If the ASSIMILATOR drive disappeared, the flash succeeded.
Firmware build fails on GitHubOpen the error shown in step 3. Typical causes: an invalid behavior reference typed in a custom sequence step. Fix the sequence and generate + build again.

11. FAQ

Why do sequences need a firmware build at all?

ZMK compiles macros into the firmware image; no runtime protocol — including the official one — can create new behaviors on the fly. Everything else (bindings, layers, names) is edited live.

Can the firmware repository be private?

Yes — it is created private by default. GitHub grants private repositories 2,000 free Actions minutes per month; one build uses about five.

Can I flash without cables, or through the other half?

No. The halves communicate by radio only, the USB ports are device-only (they cannot host each other), and the UF2 bootloader is USB-only by design — which is also what makes flashing safe: nothing can "brick" over a dropped radio link, and an interrupted USB flash simply leaves the bootloader ready to try again.

Do my manual color tweaks survive?

Live hue/saturation/brightness tweaks persist until the next color-setting sequence fires, which imposes its compiled color. To make a color permanent, set it in the app (Advanced tab or a layer's "Assign color") and rebuild.

Where is my data?

Everything lives locally: backups in backend/data/backups, staged sequences in backend/data/macros.json, settings in backend/data/configuration/config.yaml. Nothing leaves your machine except the firmware source pushed to your own GitHub repository.
